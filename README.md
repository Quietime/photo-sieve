# 照片快筛 · 原生桌面版 3.1.0

适用于 Windows 10 / 11 64 位，使用 Qt Widgets 直接显示双图，不使用浏览器、WebView 或网页服务器。JPG、PNG、TIFF、HEIC 和多种相机 RAW 可以在同一资料库内筛选。为每天约十万张照片的筛选量设计：SQLite 索引、分页队列、独立解码进程、后台预读和有限内存缓存，十万张照片不会一次加载进内存。支持本机硬盘、移动硬盘和可访问的 NAS 路径。

界面参照 iPhone 照片 App 与 apple.com 的深色设计：纯黑底让照片成为主角，顶部是文件夹名称与“未筛选 / 保留 / 已删除”分段切换，下方是浮动操作条与缩略图条。

## 使用 APP

解压 **PhotoSieve-Windows-x64.zip** 到本机目录，双击 `PhotoSieve.exe`。保留整个文件夹及 `_internal`，不能只复制 EXE。APP 已包含 Python、Qt、RAW 和 HEIC 解码依赖，无需安装 Python。

点击“打开文件夹…”，或把文件夹直接拖进窗口，会自动扫描（包括子文件夹）。以后打开 APP 会回到上次的文件夹和筛选位置；文件夹有新照片时，在右上角“⋯”菜单选“重新扫描当前文件夹”。

| 操作 | 结果 |
|---|---|
| ↑ | 保留左图，立即显示下一张 |
| ↓ | 删除左图（移入暂存），立即显示下一张 |
| → 或图片上右键 | 下一张，不修改筛选结果 |
| ← | 恢复最近一次删除，即使之后保留过其他照片 |
| Ctrl+Z | 撤回最近一次筛选或删除 |
| 按住 ↑ / ↓ / → | 按键盘重复速度连续筛选（Windows 默认每秒约 30 张） |
| 单击图片，或 Z | 在原位平滑放大到 100%；RAW 显示全尺寸画面 |
| 放大后拖动 | 查看其他区域，拖动不会退出放大 |
| 再点一次图片，或 Esc | 平滑还原双图 |

以上按键都可以在右上角“⋯”→“快捷键…”里修改。每个操作可以设一个主键和一个备用键，例如保留用 ↑ 或 P、删除用 ↓ 或 X（Lightroom 的习惯）。同一个键不能给两个操作，按“恢复默认”可还原。

按键后界面立即切到下一张，保留记录与文件移动在后台按顺序写入；如果写入失败（例如硬盘断开），照片会回到队首并显示原因。左图预览尚未读出时不会被筛选，图片会轻轻晃动提示稍等，避免删除没看到的照片。

动效：保留时左图上浮淡出，删除时下沉淡出，下一张从右侧滑入原位，新照片淡入；连续按键或按住方向键时自动跳过动画，保证速度。

## 删除文件在哪里

↓ 会把照片移入**该照片原文件夹下的 `.photo-sieve-trash`**，这不是 Windows 回收站。原文件名和路径记录在资料库中，暂存文件名使用随机编号避免冲突。在“已删除”视图里双击照片，或选中后点“恢复所选”，即可放回原位置；悬停可以看到原路径和暂存路径。

暂存照片仍占用磁盘空间，APP 不会永久清空暂存目录。手工删除 `.photo-sieve-trash` 或资料库会影响恢复，请保留它们，直到确定筛选完成。恢复遇到原位置已有同名文件会报告冲突，不覆盖。重启程序后仍可以恢复。

## 导出保留照片

点击右上角“导出”，选择目标文件夹：

- **复制**：保留原片，把副本放入目标文件夹。
- **移动**：原片转到目标文件夹，成功的照片从资料库移除；此操作不能用 ← 撤回。

导出包含任务开始时的全部保留照片，保留原文件名和子文件夹，遇到已存在的目标文件不会覆盖，会继续处理其他照片并报告失败原因。再次打开导出窗口可以查看上次的成功、失败数量，并在资源管理器中打开。

## 资料库与旧版本

默认资料库在 `%USERPROFILE%\.photo-sieve`；旧版本的保留记录、删除记录、缓存和设置都会自动沿用，不需要迁移。旧版本如果用过自定义 `--data-dir`，新 APP 也需指定同样路径：

```bat
PhotoSieve.exe --data-dir "D:\筛选记录" --folder "J:\照片"
```

打开不同的照片文件夹会为其使用独立的资料库，原文件夹的记录仍保存在 `%USERPROFILE%\.photo-sieve\libraries`。请保持照片文件夹路径稳定；拔掉外接盘后连接原盘，再重新扫描。

## 性能

APP 启动时会检测本机配置（CPU 性能核与能效核、内存、照片所在硬盘的类型），并据此调整下面的参数。检测结果显示在右上角“⋯”菜单底部。

- **预读缓冲**：内存里始终保持后面 100 到 200 张按窗口大小解码好的预览，具体数量按窗口大小和内存决定。每秒 30 到 50 张连续筛选时直接显示，不用等待。磁盘上会继续往后预生成约 1,200 张预览。
- **解码进程**：原片在独立的后台进程中解码，进程数为物理核数减 2，最多 12 个；例如 8 个性能核 + 16 个能效核的笔记本为 12 个。超过约 12 个后，笔记本的功耗上限会让收益变小，反而拖慢界面所在的核心。
  - 解码进程优先级低于界面。
  - 解码进程关闭了 Windows 的节能限速（EcoQoS），窗口最小化或被遮挡时也全速运行。
  - 某个损坏文件让解码器崩溃，只影响那一张照片；照片在机械硬盘上时，新的解码进程也不会被崩溃前占住的读盘名额卡住。
  - 系统阻止创建子进程时，自动退回线程解码。
- **相机 JPG 快速路径**：Sony 等相机的 JPG 里通常带一张约 1616 像素的 MPF 大预览。APP 只读取并解码这张预览：只读约 1 MB，比解码整张快约 10 倍。
  - 只采用相机标记为“大缩略图”的彩色预览。iPhone 等手机放在同一位置的 HDR 增益图（灰色、半尺寸）会被跳过。
  - 没有大预览，或者预览形状和原图不一致（比如加了黑边）时，照常解码整张。整张解码时按长边计算缩小倍数，1200 万到 6100 万像素的 JPG 快 1.4 到 1.9 倍。
  - 放大到 100% 时仍读取原图。
- **ARW**：A7 IV、A7R V、A1 等新机型在 ARW 里同时放了一张全尺寸 JPG（7 到 12 MB）和一张 1616 像素的预览。LibRaw 默认取最大的那张，APP 改为直接读取 1616 像素的这张，只读约 0.5 MB。用真实样张实测，每张预览的耗时：
  - A7 IV：347 毫秒降到 20 毫秒；
  - A7R V：560 毫秒降到 17 毫秒；
  - A1：542 毫秒降到 22 毫秒；
  - A7 III 等老机型只有 1616 像素这一张，速度不变（约 19 毫秒）。
  - 找不到合适的预览时交给 LibRaw，并按长边只解码到够用的尺寸。
  - 放大到 100% 时，只要 RAW 文件里有长边达到传感器 95% 的相机 JPG，就直接用它。A7 IV、A7R V、A1 都有，很多佳能、尼康机型的 RAW 也有。这张图看对焦一样清楚，颜色和预览一致，解码快约 9 倍：A7 IV 从 2.2 秒降到 0.23 秒，A1 从 3.2 秒降到 0.41 秒。它是相机处理过的 8 位图像，带机内锐化和降噪。
  - A7 IV 的 9 种 RAW 格式都实测过，两条快速路径都能用上，包括无压缩、无损压缩（大、中、小）和有损压缩，全画幅和 APS-C 都有。筛选预览从每张 127 到 413 毫秒降到 10 到 20 毫秒，放大从 0.4 到 2.0 秒降到 0.05 到 0.23 秒。
  - 没有这张大 JPG（比如 A7 III），或者它已损坏时，放大仍从传感器数据完整解码，结果写入缓存，再次放大不用等。3.1 之前缓存的传感器放大图不再使用；缓存超出上限时，会先清理最久没用过的文件，这些旧图会自然被清掉。传感器数据的色彩由 LibRaw 处理，可能与相机或厂商软件不同；新机型的支持情况取决于 LibRaw。HEIC 通过 pillow-heif 解码。
- **放大不卡顿**：放大到 100% 时，原图在后台解码，再分条转换给界面，界面每次最多停几毫秒。以前用 Qt 一次解码，6100 万像素的原图会让界面卡住约 0.6 秒。JPG 放大时也不再额外写一份约 20 MB 的缓存。
- **外接机械硬盘**：自动识别。同时最多 2 个进程读盘，JPG 一次顺序读入，避免磁头来回寻道。机械硬盘上的大 JPG 受读盘速度限制，约每秒 10 到 14 张。带 MPF 大预览的 JPG 和 ARW 不受这个限制。
- **240Hz 动画**：动画跟随屏幕刷新率（240Hz 屏幕每 4 毫秒一帧），不再固定约 60 帧。界面进程申请 1 毫秒的系统定时器精度，让解码线程和界面线程之间的切换更及时。
- **GPU 合成**：Windows 上默认用 Direct3D 11 合成窗口。
  - 显卡设备创建失败时，Qt 自动退到软件合成。
  - 如果某次启动没能正常显示窗口，下次自动改用 CPU 合成，并提示你。
  - 可以在“⋯”菜单的“GPU 合成”里关闭，重启后生效。
  - “显示帧率”可以实时查看每秒实际刷新的画面数，方便对比。
- **缓存**：磁盘预览缓存默认取缓存盘可用空间的 5%（2 到 20 GB），也可以用 `PhotoSieve.exe --cache-mb 8192` 指定。APP 不会改写原图。

以下数据在 4 核云端测试机上测得（3 个解码进程，Linux 离屏渲染，模拟连续按键）：

| 场景 | 结果 |
|---|---|
| 未预读的 Sony A7 III ARW（25 MB），每秒 30 张 | 全部跟上；预读缓冲始终不少于 99 张（中位数 156），每张都实际显示 |
| 未预读的 Sony A7 IV ARW（41 MB），每秒 50 张 | 401 次按键全部接受，0 次等待，每张都实际显示；界面卡顿 p95 为 12 毫秒 |
| 带 MPF 大预览的 2400 万像素 JPG，每秒 50 张 | 401 次按键接受 398 次，3 次需要等待；同样的 JPG 没有大预览时只有约 11 张 / 秒 |
| 没有大预览、细节极多的 2400 万像素 JPG（14 MB），每秒 40 张 | 缓冲用完后约 22 张 / 秒，受 CPU 解码速度限制 |
| 预读完成后按住 ↓ 或 ↑，每秒 40 张 | 全部跟上，每张都实际显示 |
| 连续 3,000 张 | 内存稳定，无增长 |
| 十万张资料库 | 扫描约 2.6 秒；保留约 2 毫秒、删除约 5 毫秒、恢复约 2 毫秒一张；状态刷新约 17 毫秒；已删除分页约 18 毫秒 |

24 核的电脑有 12 个解码进程，核心也更快，预计 ARW 和带大预览的 JPG 都能远超每秒 50 张。这是根据核数推算的，需要在本机实测确认。实测方法见下方“验证”。读取速度还取决于照片大小、编码、硬盘和接口。

## 从源码运行或重新打包

需要 64 位 Python 3.11 或更新版本。Windows 双击 `start_windows.bat` 安装依赖并运行。程序员也可执行：

```bat
python -m pip install -r requirements-desktop.txt
python photosieve.py
```

Windows 双击 `build_windows.bat`，会在独立构建环境内安装依赖，生成 `dist\PhotoSieve\PhotoSieve.exe` 和 `PhotoSieve-Windows-x64.zip`。使用目录形式发布，避免每次启动时解压大型依赖。发布包包含源码和依赖的开源许可证；本项目源码为 MIT。

代码结构：

- `photosieve.py`：入口。保持精简，解码进程从这里启动，不加载 Qt。
- `desktop.py`：窗口与筛选流程。
- `widgets.py`：照片视图、过渡与提示等组件。
- `theme.py`：颜色、样式和跟随刷新率的动画时钟。
- `machine.py`：本机配置检测和参数推导。
- `app.py`：资料库、解码与文件操作。

## 验证

- `python -m unittest discover -s tests -p "test_*.py"`：数据迁移、删除与持久恢复、文件冲突、解码进程、完整尺寸解码、HEIC、缓存、导出和更新器。
- `QT_QPA_PLATFORM=offscreen python tests/desktop_check.py`：真实 Qt 控件上的双图、↑↓←→、Ctrl+Z、连续按键、写入失败回滚、就地放大与还原、缩略图条、保留视图、导出、拖入文件夹和跨分页连续删除。
- `QT_QPA_PLATFORM=offscreen python tools/stress_check.py --rate 50 --source 某个ARW文件`：模拟按住按键的压力测试，报告接受的张数、等待次数、实际显示的张数、预读缓冲余量和界面卡顿。可选参数：
  - `--megapixels 24 --mpf`：带 MPF 大预览的合成 JPG；
  - `--idle 30`：先停顿一段时间再开始；
  - 环境变量 `PHOTOSIEVE_DECODERS=8`：指定解码进程数。
- `python tools/scale_check.py`：十万张资料库的扫描、查询与筛选操作耗时。

GitHub Actions 在 Windows 上运行单元测试、原生界面检查和更新检查，打包后再运行 EXE 自检（包括解码进程）与完整更新流程。

## GitHub 公开仓库与自动更新

源码仓库：https://github.com/Quietime/photo-sieve 。
正式版本：https://github.com/Quietime/photo-sieve/releases/latest 。

公开仓库更新无需 GitHub 登录、授权或令牌。更新流程：

1. APP 启动时检查 GitHub 正式版本。发现新版本时，等你停手约 2 秒后弹出提示，显示新版本号和更新内容，按钮为“下载并更新”和“以后再说”。
2. 选“下载并更新”后在后台下载，并校验 SHA256 和安装文件清单。下载时可以继续筛选，进度显示在“⋯”菜单底部。
3. 下载完成后右上角“⋯”出现蓝点。等扫描、导出和筛选记录都写完，并且停止操作 3 秒后，APP 自动关闭，替换自身文件后重新启动，回到原来的文件夹和位置。也可以在“⋯”里选“立即安装更新并重启”。
4. 重启后提示“已更新至 x.y.z”，并在后台删除下载、解压的新版文件和旧版备份。下载和解压的文件在 `%LOCALAPPDATA%\PhotoSieve\updates`。旧版备份放在 APP 文件夹里的 `.photo-sieve-update-backup`，因为文件不能跨盘移动，APP 放在 D 盘或外接硬盘时也能正常更新。确认新版文件完整后才删除旧版备份。如果文件一时被占用，会稍后重试；下次启动时也会清理残留。

打开导出、选择文件夹等对话框或菜单时，不会弹出更新提示，也不会安装。某个版本安装失败后，同一次启动不会再自动提示这个版本，手动“检查更新”仍可重试。

选“以后再说”不会下载，下次启动会再次提示；也可以随时在“⋯”里点“检查更新”。关闭“启动时检查更新”后只在手动检查时提示。照片、筛选数据库、删除暂存区和设置都不会清空。替换失败会自动恢复旧版，并在下次启动时提示原因。

APP 目录需要当前用户可写，建议解压到本机普通文件夹。更新需要 GitHub 网络连接；失败会显示状态，原版继续可用。GitHub 无登录 API 有请求次数限制，遇到限制可稍后重试。

### 发布下一版

修改程序后，在 `version.py` 提高 `APP_VERSION`（例如 `3.1.1`），更新 `RELEASE_NOTES.md`，提交并推送 `main`。GitHub Actions 自动在 Windows 上测试、打包、验证完整 EXE 更新流程，然后创建对应 tag 和 Release，并上传 ZIP、`update.json` 与 SHA256 清单。已发布版本不覆盖；仅改代码而不提高版本会运行构建验证，但不会发布另一个同版本包。

本地发布也可运行 `build_windows.bat`，产物在 `release/`。不要上传照片、数据库、缓存或 GitHub 令牌；`.gitignore` 已排除常见本地数据与构建文件。
